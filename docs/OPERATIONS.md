# 운영 정책·절차

상태: 초안 (2026-11-23, Phase 4 관리자 도구 절차·모니터링 2026-11-25, Phase 5 백업·장애·사고 체크리스트 2026-11-25)

> 운영자 검토 전 초안이다. 법령 해석이 필요한 부분은 법률 검토 전까지 확정하지 않는다. 이용자에게 공개되는 요약은 `/policies/operations` 화면에 싣는다(원문: `src/content/policies/operations.md` — 이 문서의 §1~§4 중 이용자 대상 부분. 이 문서를 고치면 함께 고친다).

관련 문서: [PRD](./PRD.md) · [SECURITY](./SECURITY.md) · [DB_SCHEMA](./DB_SCHEMA.md) · [TERMS_DRAFT](./policies/TERMS_DRAFT.md) · [PRIVACY_DRAFT](./policies/PRIVACY_DRAFT.md)

## 1. 기본 원칙

- 서비스는 모임 정보를 모아 보여주고 신청·확정을 돕는다. 오프라인 모임 현장을 운영하거나 감독하지 않는다.
- 신고만으로 자동 제재하지 않는다. 관리자가 직접 확인하고, 조치와 사유를 기록하며, 이의제기 경로를 둔다.
- 제재는 필요한 만큼만, 단계적으로 한다.
- 운영 문의·이의제기·개인정보 요청 창구는 운영 이메일 하나로 모은다. `BLOCKED:` 주소 미정.

## 2. 운영 규정

### 2.1 오프라인 안전 수칙 (이용자 안내)

- 처음 만나는 모임은 보드게임 카페 등 공개된 장소를 권장한다. 개인 주거 공간 모임은 신중히 판단한다.
- 연락처·주소 등 개인정보는 필요한 만큼만, 스스로 판단해 공유한다. 서비스는 연락처를 수집·중개하지 않는다.
- 불편하거나 위험하다고 느끼면 언제든 자리를 떠나도 된다. 위급한 상황은 112(경찰)·119(구조·구급)에 먼저 연락한다.
- 음주를 강요하지 않는다. 공간 이용료는 각자 공간의 안내에 따른다.

### 2.2 노쇼

- 확정 후 참석이 어려우면 시작 전에 직접 신청을 취소한다.
- 모임장은 시작 후~종료 7일 이내에 출석(`attended`/`absent`)을 기록할 수 있다. 출석 기록은 다른 이용자에게 공개하지 않는다.
- 노쇼만으로 자동 제재하지 않는다. 반복 불참 기록과 `no_show` 신고가 함께 있을 때 관리자가 검토한다(기준 횟수는 미정, 운영 데이터를 보고 결정).
- 모임장이 출석 기록을 악용(허위 불참 표시)한 정황이 있으면 모임장도 검토 대상이다.

### 2.3 성희롱·괴롭힘·차별

- 원치 않는 신체 접촉, 성적 발언, 외모 평가, 사적 만남 강요, 반복 연락, 혐오·차별 표현을 금지한다.
- 신고 사유 `harassment`. 피해 신고는 다른 신고보다 먼저 검토한다.
- 신고자 정보를 상대방에게 알리지 않는다.
- 범죄 피해가 의심되면 수사기관 신고를 안내한다. 수사기관 요청에 따른 자료 제공 절차는 `미확인:` 법률 검토 필요.

### 2.4 상업적 권유·스팸

- 모임을 빌미로 한 영업·판매·다단계·종교 및 정치 포교·회원 모집, 반복 홍보성 모임 개설을 금지한다. 신고 사유 `commercial`, `spam`.
- 공간(카페·파티룸) 홍보는 공간 정보 메뉴로만 다루며 관리자가 등록한다.
- `미확인:` 모임장이 공간 이용료 외 별도 회비·선입금을 받는 것을 허용할지. 제안: MVP에서는 공간 이용료 각자 부담 안내만 허용하고 별도 회비·선입금 요구는 금지.
- `미확인:` 소개문에 외부 연락 수단(오픈채팅 링크 등)을 적는 것을 허용할지. 알림·채팅이 없어 일정 변경을 알릴 방법이 없다는 점과 개인정보·스팸 위험을 함께 고려해 운영자가 결정한다. 어느 경우든 앱은 URL을 자동 링크로 만들지 않는다.

### 2.5 금전성 홀덤 금지

- 홀덤(`holdem_social`) 카테고리는 **금전·재물을 걸지 않는 취미 모임만** 허용한다.
- 금지: 베팅, 칩의 현금·상품 환전, 상금·경품, 참가비를 칩으로 바꾸는 방식, 순위에 따른 보상, 외부 도박 사이트·업장 홍보.
- 모임 생성 시 홀덤을 고르면 안내 문구와 동의 체크가 필수다(동의 사실은 감사 로그에 남긴다).
- 위반 의심은 신고 사유 `gambling`. 확인되면 모임 숨김 또는 취소, 반복 시 계정 이용 제한.
- 관련 법령(도박 관련 규정 등)의 적용 범위는 `미확인:` 법률 검토 필요. 이 문서는 법적 판단을 대신하지 않는다.

### 2.6 미성년자 (미확인)

- `미확인:` 만 14세 미만 이용자의 개인정보 처리에는 법정대리인 동의 관련 규정이 있는 것으로 알려져 있다. 현재 서비스에는 법정대리인 동의 절차가 없다.
- 제안: 만 14세 미만 가입 불가를 약관에 명시하고 최초 설정에서 "만 14세 이상입니다" 확인을 받는다. 연령을 증명받지는 않는다(본인확인 미도입).
- `미확인:` 청소년의 심야 모임·주류 제공 공간 이용 관련 제한. 법률 검토 전까지 모임장에게 공간 규정을 따르도록 안내만 한다.

### 2.7 기타 금지

- 타인 사칭, 실명 인증·제휴 등 사실이 아닌 표시, 타인의 개인정보 게시, 불법 행위 모의, 서비스 운영 방해(자동화된 대량 요청 등).
- 소개·닉네임에 전화번호·주소 등 개인정보를 적지 않도록 안내한다.

## 3. 신고 처리 절차

| 단계 | 상태 | 관리자 작업 |
|---|---|---|
| 1. 접수 | `received` | 신고가 쌓이면 목록에서 확인. 자동 조치 없음 |
| 2. 검토 | `reviewing` | 대상 모임·프로필 내용, 신고 본문, 같은 대상의 다른 신고, 필요한 경우 감사 로그 확인 |
| 3. 조치 | `resolved` | 조치 없음 / 모임 숨김(`admin_set_meeting_hidden`, 사유 필수) / 모임 취소 / 계정 이용 제한(`admin_set_user_status`) 중 선택 |
| 4. 기각 | `dismissed` | 위반이 확인되지 않음 |
| 5. 기록 | - | `admin_note`에 판단 근거를 사실 위주로 적는다. 불필요한 개인정보·추측은 적지 않는다 |

- 제재 단계(제안): 주의 안내 → 콘텐츠 숨김 → 계정 이용 제한 → 중대·반복 위반 시 탈퇴 처리 검토.
- 서비스에 알림 기능이 없으므로 제재 사실은 이용자가 로그인했을 때 안내 띠로 보인다. 개별 연락은 운영 이메일로만 한다(`BLOCKED:`).
- 이의제기: 이용자가 운영 이메일로 요청 → 처음 조치하지 않은 관리자가 다시 검토(관리자가 1명이면 기록을 남기고 재검토). 결과를 기록한다.
- 처리 목표 기간은 미정(운영 인력 확정 후 결정).

## 4. 공간 정보 등록 기준

- 등록 주체: 관리자만(`venues` 쓰기는 `is_admin()`).
- 출처: 공간 운영 주체가 직접 운영하는 공식 홈페이지·공식 예약 페이지·공식 SNS. 출처를 확인한 시각을 `info_verified_at`에 기록한다.
- 링크는 `https://`만. 확인되지 않은 예약 링크는 넣지 않는다.
- 표시하지 않는 것: 실시간 영업 여부, 좌석·예약 가능 시간, 가격. 화면에 "공식 채널에서 확인해 주세요"를 표시한다.
- 다른 서비스의 사진·리뷰·소개문을 복사하지 않는다. 사진은 라이선스가 확인된 경우에만(현재 없음).
- "제휴", "인증" 표기를 하지 않는다(제휴 기능 없음).
- 공간 측의 정정·삭제 요청은 확인 후 반영하고, 삭제 대신 `is_public=false`로 비공개 처리한다.
- 정기 재확인 주기: 제안 분기 1회(운영자 결정). 폐업 확인 시 비공개.

## 5. 개인정보 요청 처리

| 요청 | 처리 |
|---|---|
| 열람 | 프로필 화면에서 본인 공개 정보 확인. 그 외 저장 항목은 운영 이메일 요청 시 안내 |
| 정정 | 프로필 화면에서 직접 수정 |
| 삭제(탈퇴) | 프로필 → 탈퇴 요청(`request_account_deletion`) → 운영자가 계정 삭제 |
| 처리 정지·기타 | 운영 이메일로 접수(`BLOCKED:`) |

- 이메일 요청은 해당 계정의 로그인 이메일에서 보낸 경우에만 처리한다(운영자가 대시보드에서 대조).
- `미확인:` 법정 처리 기한과 거절 사유 — 법률 검토 필요.

탈퇴 계정 삭제(수동 절차, 향후 service role Edge Function으로 대체 가능):
1. SQL Editor에서 요청 목록 확인:
   ```sql
   select user_id, deletion_requested_at from public.user_private
   where deletion_requested_at is not null order by deletion_requested_at;
   ```
2. 처리 중인 신고·분쟁과 관련된 계정인지 확인하고 보관 정책([PRIVACY_DRAFT §5](./policies/PRIVACY_DRAFT.md#5-보유-및-이용-기간))에 따라 처리 시점을 정한다.
3. Supabase 대시보드 → Authentication → Users에서 해당 사용자 삭제. 연쇄 삭제 범위는 [DB_SCHEMA §13](./DB_SCHEMA.md#13-탈퇴삭제와-fk-동작).
4. 운영 기록에 처리일과 사용자 id만 남긴다(이메일 미기록).

## 6. 관리자 작업 절차

- 관리자 지정·해제는 [DEPLOYMENT §3.4](./DEPLOYMENT.md#34-최초-관리자-지정)의 SQL로만 한다.
- 관리자 권한은 **active 계정에서만** 동작한다(마이그레이션 9, [SECURITY §3.1](./SECURITY.md#31-역할--동작-매트릭스와-근거-테스트-phase-5)). 관리자 계정을 이용 제한하거나 관리자가 탈퇴를 요청하면 그 즉시 관리자 권한(관리자 도구·숨김 모임 조회·공간·카테고리 쓰기)도 멈추고, 제한을 풀면 다시 돌아온다. 관리자 자격을 완전히 빼려면 `admin_roles` 행을 삭제한다([DEPLOYMENT §3.4](./DEPLOYMENT.md#34-최초-관리자-지정)의 해제 SQL). 관리자는 자기 계정을 이용 제한할 수 없으므로 실수로 자기 권한을 잃지 않는다(`admin_set_user_status`가 본인 대상을 거부).
- 관리자 화면의 모든 변경은 감사 로그에 남는다(RPC 또는 테이블 트리거). 공간·카테고리·게임을 SQL Editor로 고치면 트리거가 actor_id 없이 기록하므로, 누가 왜 고쳤는지는 운영 기록에 따로 남긴다. 그 밖의 테이블을 SQL Editor로 고친 경우에도 같은 내용을 수동으로 기록한다.

### 6.1 관리자 도구(`/admin`) 사용 절차

진입: 관리자 계정으로 로그인 → 마이 → "관리자 도구 열기". 헤더·하단 내비에는 메뉴가 없다. 화면이 열리더라도 모든 데이터·동작은 서버가 관리자 여부를 다시 확인한다(관리자가 아니면 실패).

| 탭 | 하는 일 | 서버 동작 · 기록 |
|---|---|---|
| 신고 | 상태 칩으로 접수·검토 중 신고를 확인 → 대상(모임 상세 링크 / 사용자 닉네임)·사유·본문·신고자 확인 → 처리 상태와 관리자 메모(신고자에게 비공개, 1000자) 저장 | `admin_update_report` → audit `admin.report_update`. 처리 완료·기각이면 처리자·처리 시각 기록 |
| 모임 | 제목·게임명 검색, "숨김만 보기" → 숨기기(사유 필수 200자, 모임장에게 보임) / 숨김 해제 / 모임 취소(종료 전까지, 사유 선택) | `admin_set_meeting_hidden` → `admin.meeting_hidden`, `cancel_meeting` → `meeting.cancel`(by_admin). 숨겨도 참가 신청 상태는 그대로, 취소하면 게스트 신청이 '모임 취소'로 바뀐다 |
| 사용자 | 닉네임 또는 사용자 id로 검색(최근 30일 신고 수 함께 표시) → 이용 제한 / 제한 해제(처리 메모 200자) | `admin_set_user_status` → `admin.user_status`(메모 포함). 본인·탈퇴 요청 계정은 바꿀 수 없다. 제한해도 그 사용자의 모임은 자동 취소되지 않으므로 필요하면 모임 탭에서 따로 처리 |
| 공간 | 새 공간 등록·수정(§4 기준, https 링크만, 정보 확인일) → 공개/비공개 전환(삭제 대신) | venues 테이블 직접 쓰기(RLS) → 트리거 audit `admin.venue_create`·`admin.venue_update`(바뀐 필드 이름만). `created_by`는 요청자로 자동 기록 |
| 카테고리 | 활성/비활성 전환 | categories 직접 쓰기 → `admin.category_update`. 이름·설명·순서 변경은 화면에 없다 → SQL Editor로 고치고 프론트 상수(`src/domain/categories.ts`)를 함께 배포 |

신고 처리 권장 순서: ① 접수 신고를 "검토 중"으로 바꾸고 메모에 확인 항목 기록 → ② 대상 모임·프로필 확인(필요하면 감사 로그 조회) → ③ 모임·사용자 탭에서 조치 → ④ 신고를 "처리 완료"(조치함) 또는 "기각"(위반 없음)으로 바꾸고 판단 근거를 사실 위주로 메모. 같은 대상의 신고가 처리 중이면 신고자는 다시 신고할 수 없으므로(중복 방지), 처리를 미루지 않는다.
- 운영 DB에서 직접 수정은 최소화하고, 스키마 변경은 반드시 마이그레이션으로 한다.
- 이용 제한된 사용자의 기존 주최 모임은 자동 취소되지 않는다. 필요하면 관리자가 숨김·취소를 따로 판단한다.
- 카테고리는 삭제하지 않고 비활성화한다(기존 모임 참조 유지).

## 7. 모니터링 최소안

**기본적으로 외부 모니터링·오류 수집 도구를 쓰지 않는다**(가입·유료 서비스 없음, 개인정보처리방침에 새 처리자를 추가하지 않아도 됨). 대신 운영자가 주 1회 직접 확인한다(제안).

- Supabase 대시보드: DB 용량, API 요청량, Auth 사용자 수, 오류 로그. `미확인:` 무료 플랜 한도 수치.
- Cloudflare Pages: 최근 빌드·배포 성공 여부. `미확인:` 무료 플랜에서 볼 수 있는 요청 분석 범위.
- 공식 상태 페이지(장애 때): Cloudflare Status, Supabase Status.
- SQL Editor 점검 쿼리(주 1회 제안):
  ```sql
  -- 1) 신고 적체: 상태별 건수와 가장 오래된 미처리 신고
  select status, count(*), min(created_at) as oldest
  from public.reports group by status order by status;
  select id, target_type, reason, created_at from public.reports
  where status in ('received', 'reviewing') and created_at < now() - interval '3 days'
  order by created_at limit 20;

  -- 2) 숨김 모임 수와 최근 숨김
  select count(*) as hidden_meetings from public.meetings where is_hidden;
  select id, title, hidden_reason, updated_at from public.meetings
  where is_hidden order by updated_at desc limit 20;

  -- 3) 최근 관리자 작업(감사 로그) — 누가 무엇을 했는지
  select created_at, actor_id, action, target_type, target_id, meta
  from public.audit_logs
  where action like 'admin.%' or (action = 'meeting.cancel' and (meta ->> 'by_admin')::boolean)
  order by created_at desc limit 50;

  -- 4) 모임 대량 생성 의심(7일)
  select actor_id, count(*) from public.audit_logs
  where action = 'meeting.create' and created_at > now() - interval '7 days'
  group by actor_id order by count(*) desc limit 10;

  -- 5) 이용 제한 계정 수, 오래 확인하지 않은 공개 공간(90일)
  select count(*) as restricted from public.profiles where status = 'restricted';
  select id, name, info_verified_at from public.venues
  where is_public and (info_verified_at is null or info_verified_at < now() - interval '90 days')
  order by info_verified_at nulls first;

  -- 6) 관리자 목록(분기마다). status가 active가 아닌 행은 지금 관리자 권한이 멈춘 계정 — 계속 둘지, admin_roles에서 지울지 정한다
  select ar.user_id, p.nickname, p.status, ar.granted_at
  from public.admin_roles ar join public.profiles p on p.id = ar.user_id order by ar.granted_at;
  ```
- 앱에는 오류 수집 도구가 없다. 브라우저 콘솔 출력도 개발 모드에서만 나온다([SECURITY §11](./SECURITY.md#11-로그와-개인정보)).
- 이용자 오류 제보는 운영 이메일로 받는다(`BLOCKED:`).
- 도입 후보(지금은 가입·설정하지 않음 — 도입하려면 사용자 결정, 개인정보처리방침·CSP connect-src 갱신 필요): 외부 가동 확인(업타임 점검) 서비스, 브라우저 오류 수집 서비스, Cloudflare Web Analytics, Supabase 로그 보관 기간이 긴 유료 플랜.

## 8. 백업

- `미확인:` Supabase 플랜별 자동 백업의 범위·주기·보관 기간·복원 방법·시점 복구(PITR) 제공 여부. 무료 플랜에서 내려받을 수 있는 백업이 있는지 대시보드(Database → Backups)에서 확인하고 이 문서에 적는다. 자동 백업이 있어도 아래 수동 백업을 함께 한다.
- 수동 백업(운영자 로컬 PC, PostgreSQL 클라이언트 도구 필요 — `pg_dump` 버전은 서버 버전 이상):

  ```bash
  # 연결 문자열은 대시보드 Connect 화면 값(직접 연결 또는 세션 풀러). 셸에서만 쓰고 파일·명령 기록에 남기지 않는다.
  pg_dump "<연결 문자열>" --schema=public --no-owner --no-privileges -Fc -f hanpan_public_YYYYMMDD.dump
  ```
  - 대안: `npx supabase db dump --db-url "<연결 문자열>"`(스키마) + `--data-only`(데이터). `미확인:` 설치 버전 옵션.
  - `auth` 스키마(로그인 계정)는 위 명령에 포함되지 않는다. 계정 데이터 백업 범위·방법은 `미확인`(Supabase 자동 백업에 포함되는지 확인).
- 주기(제안): 주 1회 정기 + **운영 마이그레이션 적용 직전** + 대량 관리 작업(일괄 숨김·삭제) 직전.
- 보관 원칙:
  - 덤프 파일에는 개인정보(닉네임·신청 메시지·신고 본문 등)가 들어 있다. **저장소(Git)·메신저·이메일·공유 드라이브의 공개 폴더에 올리지 않는다.**
  - 암호화해서 보관한다(예: 암호화된 디스크·볼륨, 또는 파일 단위 암호화 도구로 암호화 후 보관). 암호는 비밀번호 관리자에 둔다.
  - 최근 N개만 유지하고 기간이 지난 파일은 삭제한다(N·기간은 §10 운영 정책에서 결정). 탈퇴 처리한 이용자의 데이터가 오래된 백업에 남는 점을 개인정보처리방침의 보관 기간과 맞춘다(`미확인:` 법률 검토).
  - 백업 일시·파일 이름·보관 위치를 운영 기록에 남긴다(내용은 적지 않음).
- 복원 시험: 분기 1회(제안) 개발용 프로젝트에 `pg_restore`로 복원해 앱이 뜨는지 확인한다. 운영 프로젝트에 복원하는 것은 마지막 수단이다([DEPLOYMENT §10](./DEPLOYMENT.md#10-롤백)).

## 9. 장애·사고 체크리스트

공통: ① 시각·증상·영향 범위를 기록한다 ② 원인이 확인될 때까지 증거(로그·화면)를 지우지 않는다 ③ 끝나면 원인·영향·조치·재발 방지를 운영 기록과 CHANGELOG에 남긴다. 이용자 공지 수단은 `BLOCKED:`(서비스 내 안내 띠 등 미정, 운영 이메일 미정).

**A. 서비스 다운(접속 불가·흰 화면·로그인 불가)**
1. 다른 네트워크·기기에서도 같은지 확인. Cloudflare·Supabase 공식 상태 페이지 확인.
2. 최근 배포 직후라면 Pages에서 직전 정상 배포로 롤백([DEPLOYMENT §10](./DEPLOYMENT.md#10-롤백)).
3. 화면은 뜨는데 목록이 "정보를 불러오지 못했어요"면 Supabase 쪽(일시중지된 무료 프로젝트인지, API 한도 초과인지) 대시보드 확인. `미확인:` 무료 플랜 비활성 일시중지 정책.
4. 로그인만 실패하면 Auth URL 설정·OAuth client secret 만료·공급자 콘솔 변경 확인.
5. 최근 마이그레이션이 원인이면 수정 마이그레이션(fix-forward) 또는 백업 복원 판단([DEPLOYMENT §10](./DEPLOYMENT.md#10-롤백)).

**B. 키 노출 의심**
- anon(publishable) 키: **원래 공개 값**(브라우저 번들에 들어 있음)이다. 노출 자체는 사고가 아니며 보호 경계는 RLS·RPC다. 다만 남용(대량 요청)이 의심되면 키를 교체하고 Cloudflare 레이트 리밋을 검토한다.
- service role/secret 키·DB 비밀번호·OAuth client secret이 저장소·채팅·로그·번들에 노출됐다면 즉시 교체한다. 순서:
  1. 새 키(또는 비밀번호·secret)를 발급한다(Supabase 대시보드 API 키 화면 / DB 비밀번호 재설정 / Google·Kakao 콘솔).
  2. 새 값을 쓰는 곳을 갱신한다: anon 키 교체라면 Pages 환경 변수(운영·프리뷰) → 재배포. OAuth secret은 Supabase provider 설정. DB 비밀번호는 운영자 로컬 연결 설정.
  3. 이전 키를 폐기(비활성화)한다 — 새 값이 반영된 것을 확인한 뒤.
  4. 노출된 동안의 요청·감사 로그(`audit_logs`, Supabase 로그)를 확인한다. service role 키는 RLS를 우회하므로 데이터 변경·조회 흔적을 본다.
  5. Git 기록에 들어갔다면 기록에서 지우는 것만으로는 부족하다(이미 복제됐을 수 있음) — 교체가 먼저다.
  - `미확인:` Supabase 키 형식별(JWT·publishable/secret) 교체·폐기 절차와 JWT 비밀 교체 시 기존 세션 영향.

**C. 개인정보 유출 의심**
1. 원인 차단: 문제 기능 중단(앱 롤백, 해당 RPC 권한 회수를 담은 긴급 마이그레이션), 관련 키 교체(B).
2. 증거 보존: 감사 로그·Supabase 로그·Cloudflare 로그를 내려받아 암호화 보관(로그 보관 기간이 짧을 수 있으니 먼저).
3. 영향 범위 파악: 어떤 항목(닉네임·신청 메시지·신고 본문·이메일)이 누구에게 얼마나 노출됐는지.
4. `미확인:` **법령상 통지·신고 의무와 기한(이용자 통지, 감독기관 신고 등)은 법률 검토가 필요하다.** 이 문서는 법적 판단을 대신하지 않는다. 운영자는 사고 인지 즉시 법률 자문을 구한다.
5. 재발 방지: 원인 수정 + 해당 경우를 DB 테스트로 추가.

**D. 스팸·어뷰징 급증**
1. §7 점검 쿼리 4)로 대량 생성 계정, 신고 목록으로 대상 확인.
2. 관리자 도구에서 모임 숨김 → 계정 이용 제한(사유 메모). 이용 제한해도 그 계정의 모임은 자동 취소되지 않으므로 필요하면 취소.
3. 레이트 리밋(모임 24시간 5개·진행 예정 10개, 신고 하루 10건)은 DB에 고정돼 있다. 바꾸려면 마이그레이션이 필요하다.
4. 가입 자체가 대량이면 Supabase Auth 설정(`미확인:` 제공되는 가입 제한·CAPTCHA 옵션)과 Cloudflare 레이트 리밋 규칙(`미확인:` 무료 플랜 범위)을 검토한다.

**E. 금전성 도박(홀덤) 신고**
1. 신고(`gambling`)를 "검토 중"으로 바꾸고 모임 소개·유의사항·모임장 프로필을 확인한다(§2.5 기준: 베팅·환전·상금·경품·참가비의 칩 교환·외부 업장 홍보).
2. 위반 정황이 있으면 모임을 숨기고(사유 필수 — 모임장에게 보임) 필요하면 취소한다. 반복이면 계정 이용 제한.
3. 판단 근거를 관리자 메모에 사실 위주로 적는다. 신고자 정보는 상대에게 알리지 않는다.
4. 범죄 정황(실제 금전 거래 증거 등)이 있으면 수사기관 신고를 안내한다. `미확인:` 수사기관 자료 요청 대응·관련 법령 적용 범위 — 법률 검토 필요.
